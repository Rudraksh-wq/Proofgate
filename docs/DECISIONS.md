# Design decisions

One line per change to the plan's design, with the reason. Newest last.

| Date | Decision | Why |
|---|---|---|
| 2026-11-20 | Docker is never required. It stays an optional backend, used only where it already exists (for example GitHub Actions runners). | The development machine is a Windows laptop without Docker; a hard Docker dependency made branches 15, 16 and the live checks impossible to run. |
| 2026-11-20 | Layer 9 scans only `.next/static`, `dist/` and `build/`, and only when they already exist (a missing build is a note under `--full`). | `.next/server` is server-side code that may legitimately hold server env values; and a scan must never run a build. |
| 2026-11-20 | Layer 9 reuses Layer 1's patterns and fingerprints and tags its hits `proofgate-bundle`. | The same secret found by both layers then merges into one finding with `confirmed_by = 2` instead of two alerts. |
| 2026-11-20 | Layer 6 decides "committed `.env`" with `git check-ignore` inside a repository and the project's `.gitignore` otherwise. | A `.env` that is git-ignored is the correct setup and must not be flagged; a fixture outside a repository still needs an answer. |
| 2026-11-20 | Checkov findings are `medium` confidence and only from the SARIF it writes to a temporary directory. | Checkov is not installed on the laptop, so the adapter is verified against a hand-written sample only: pending real-tool verification. |
| 2026-11-21 | `accepted.yml` is a strict YAML subset read by our own parser, not PyYAML. | PyYAML is a dev-only dependency; the runtime must not grow a new one for one small file. The test suite checks the output is real YAML. |
| 2026-11-21 | An accepted-risk entry is applied in `run_scan`, so the CLI, MCP server and hooks all see the same statuses; a proven critical needs `forced: true` both when writing and when applying. | A hand-edited file must not be able to silently accept a proven critical. |
| 2026-11-21 | `.gitignore` uses `**/.proofgate/*` plus an exception for `accepted.yml`. | Ignoring the whole folder would also ignore the one file that must be committed; the `**/` form keeps nested projects covered. |
| 2026-11-21 | Supabase work goes through a `SupabaseTarget` with `hosted` and `local` backends (`--backend`, `PROOFGATE_SUPABASE_BACKEND`); the Supabase CLI is not needed. | No Docker on the development laptop; migrations, variant switching and Splinter all work over one psycopg connection. |
| 2026-11-21 | A hosted project needs its ref in `PROOFGATE_ALLOWED_PROJECT_REFS` AND `--i-own-this` (or `PROOFGATE_I_OWN_THIS=1`); localhost needs neither. Refs match exactly, no wildcards, and the DB URL must belong to the same project. | The probe plants rows and creates users: it must never be pointed at a project the user did not name. |
| 2026-11-21 | `reset-demo` drops only `public.notes` and `public.run_sql`, and refuses any folder without `supabase/variants`. | A reset against a hosted project must not be able to touch anything but the demo's own objects. |
| 2026-11-21 | Live Splinter runs only with `--full`, and an unavailable/refused backend or a missing `splinter.sql` is a recorded skip; an unexpected live failure is an `error`, never a clean result. | A plain `scan` must stay offline and fast; a broken live check must not look like a pass. |
| 2026-11-21 | `psycopg` is an optional extra (`proofgate[supabase]`), not a core dependency. | Most users only need the static checks. |
| 2026-11-21 | Layer 7 is native ZAP (zap.bat/zap.sh, Automation Framework plan, passive only), then Docker ZAP only if `docker info` works, then the built-in `dast-lite` checks; `dast-lite` findings are labelled and never called equal to ZAP. | No Docker on the laptop; a basic honest check is better than no layer, and the label stops it being mistaken for a real ZAP scan. |
| 2026-11-21 | Layer 7 refuses any non-localhost target with no `--i-own-this` override, runs only with `--full`, and caches its result per source hash. | It starts the app and sends traffic; the override that exists for layer 8 would make it a general scanner. |
| 2026-11-21 | Everything that needs Linux or Docker (`supabase start`, `semgrep --test`, Docker ZAP) is verified by `.github/workflows/live-stack.yml` on ubuntu-latest, with every action pinned by SHA and no secrets. | Docker is not used on the development laptop; a free runner has it. The workflow checks each RLS variant by behaviour (anon / another user reading a planted row), not only by its SQL. |
| 2026-11-21 | New-format Supabase keys are handled: `sb_secret_...` is a critical secret (masked, blocked by the hook, flagged in code and bundles); `sb_publishable_...` is public like the anon key; `sb_` keys are sent as `apikey` only, never as a Bearer token. | New projects no longer issue JWT keys, so the JWT role decoder alone would have missed the service-level key. |
| 2026-11-21 | A `.env` that is a folder of `*.env` files is read; the repo-root `.env` is a fallback only for the demo project. | The user's file is `.env/SUPABASE.env`; an explicit `--project` must never pick up the real project by accident. |
| 2026-11-21 | The live Layer 5 check reads the database catalogs into the same `Schema` model as the migrations and reuses `check_schema`. | Splinter does not judge policy logic (it missed variant B); the contract-aware checks do, and running them on the live database also catches migrations that were never installed. |
| 2026-11-21 | `tools.lock.json` is saved one tool per line and still ships with no hashes (observed versions and hashes are listed in `docs/VERIFICATION.md`). Downloading unverified Go binaries (Gitleaks, Betterleaks, OSV-Scanner) was not done. | Small, reviewable diffs; a hash of a venv launcher is machine-specific; fetching and running unvetted binaries needs the user's approval. |
| 2026-11-21 | `docs/VERIFICATION.md` is the single list of what is verified against a real tool and what is still pending. | The README and website make claims; this is where each one is backed or labelled. |
| 2026-11-21 | The Supabase probe works through the project's own HTTP API (Auth admin users, PostgREST as anon and as user B), not through SQL role switching. | It is what a real attacker can reach; the SQL check in `ci_live_check.py` only confirms the policies. New `sb_` keys go in `apikey` only. |
| 2026-11-21 | A live fix is verified by replaying EVERY migration (variant at its slot) on the real database, re-probing the patched copy, and then replaying the ORIGINAL state again after each candidate. | A rejected or merely evaluated candidate must never leave the test project changed; Guard B means the migration really runs. |
| 2026-11-21 | In live mode "no finding after the fix" only counts if the same attack was re-run and HELD. | An unreachable route or a dev server that failed to start would otherwise look like a fixed bug. |
| 2026-11-21 | A live Next.js fix is evaluated in a copy under `<project>/.proofgate/tmp/`, not in the system temp folder. | Node must find the real `node_modules` by walking up; links break webpack and copying it is too large. Patches still apply to the copy only. |
